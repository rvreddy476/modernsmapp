# Audit: dating backend (dating-service, its chat, payments, media and gateway edges)

Branch `codex/module-01-02-launch-safety`. Read-only audit: no edits except this file, no git writes, no databases, no deploys.
Paths are relative to `Architecture/services/dating-service/` unless they start with `Architecture/`, `chat-service/`, `deploy/` or `identity-platform/`.

Covered: discovery (`/pulse/today`, Nebula, pass, rewind, explain, picks), the candidate query and deck cache (`store/pulse.go`, `service/pulse.go`), location snapping and distance buckets (`store/geo.go`, `store/location.go`), person cards, sparks, liked-you, match formation and the chat saga (`service/spark.go`, `service/match.go`, `store/matches.go`), unmatch and block, photos and their media delivery (`service/photos.go`, `store/photo_safety.go`, `Architecture/services/media-service/internal/service/dating_photo.go`), selfie and Aadhaar verification, vouches, safety (panic, location shares, meets, reports), premium purchases and the payment-event consumer (`internal/payments`, `store/premium.go`), data export, purge, admin routes (`http/auth.go`, `http/admin_token.go`), the boot schema (`database/setup.sql` via `database/embed.go`), `deploy/services/dating-service/values-prod.yaml`, the message-service dating integration (`chat-service/services/message-service/internal/events/dating_consumer.go`, `internal/service/message.go`, the `/internal/v1/chat/conversations/dating-match*` handlers) and the gateway front (`Architecture/services/api-gateway/cmd/server/main.go:732,1050-1069,1365-1368`).

Launch posture that changes some severities: the gateway keeps `/v1/dating` closed except to `DATING_PILOT_USER_IDS` until `DATING_PUBLIC_ENABLED` is true. Prod runs one replica, no HPA, `DIGILOCKER_MODE: disabled`, and every M-mechanic flag (`DATING_*_ENABLED`) defaults to off outside local/dev (`http/boot_config.go:465-470`), so in prod the deck is the 24 h cached deck, liked-you is ungated, and travel, hide-known, rewind and picks are off.

## HIGH

### H1. Passing any user id, then opening Nebula, returns that user's full dating card even when they are paused, hidden, restricted or under review
- **Files:**
  - `POST /v1/dating/pulse/:candidateId/pass` (`http/handler.go:138`, `http/handler_pulse.go:110-130`, `service/pulse.go:682-709`, `store/pulse.go:610-634`) inserts a `dating_passes` row for any UUID. Nothing checks that the candidate was ever in the caller's deck, is visible to them, or even has a profile. The caller does not need to be an adult with a profile (no `requireAdult` on this path).
  - `GET /v1/dating/pulse/nebula` (`handler.go:132`, `service/pulse.go:616-655`) lists those passes through `ListPassedCandidates` (`store/pulse.go:639-660`), whose only profile filter is `visibleProfilePredicate` (`store/safety.go:190-195`: not deleted, not suspended). It then loads each card with `GetCandidateForViewer` (`store/pulse.go:486-497`), which checks blocks, incognito and "not suspended/deleted" only.
  - Not applied, unlike `FetchCandidates` (`store/pulse.go:240-300`): `profile_status = 'active'`, `paused = false`, `visible_to_public = true`, the 18+ birth-date floor, the risk levels `hide_from_discovery`/`chat_hold`/`admin_review`/`suspend`, the two-way gender preference (lane D10) and hide-known (M16).
  - `buildCard` (`service/pulse.go:530-600`) returns first name, age, city, bio, prompts, languages, lifestyle basics, every approved photo (as image routes), trust tier, last-active bucket and a distance bucket computed live from the target's current snapped location.
  - Rewind uses the same loader (`service/rewind.go:155-160`), so it carries the same gap once `DATING_REWIND_ENABLED` is on.
- **Scenario:** Platform user ids are not secret (they come back on every social profile, post and comment). A coworker or ex takes the victim's id from the social app and sends `POST /pulse/<victim>/pass`, then `GET /pulse/nebula`. They learn that the victim has a dating profile and read it, including the photos, even though the victim paused it, set `visible_to_public=false`, or is held in `pending_review`. Whether the victim has a gender preference that excludes the attacker makes no difference. Because the distance bucket is recomputed on every Nebula call, an attacker who moves their own location (10 moves a day, `store/location.go:43-45`) can narrow a paused user's position to the 1.1 km grid. The same path also shows profiles that `restrictUnderageProfile` (`service/profile.go:301-303`) moved to `restricted` after identity reported an under-18 birth date, so an adult can view a minor's dating photos and bio.
- **Fix:** In `PassCandidateFrom`, refuse (404 `CANDIDATE_UNAVAILABLE`) unless the candidate is in the caller's current deck or picks, the same rule `canViewPerson` (`service/person.go:362-401`) applies, and require `requireAdult` on the caller. Give `GetCandidateForViewer` the full discovery visibility predicate: active status, not paused, `visible_to_public`, 18+, no restrictive risk level, gender in both directions, and hide-known when it is on. Factor that predicate out of `FetchCandidates` so the two cannot drift. Add a guard test: pass a paused profile's id and expect it absent from Nebula.

### H2. Suspension, `chat_hold` and self-delete leave every dating chat open; block and unmatch close the chat only through a best-effort Kafka publish
- **Files:**
  - message-service refuses a dating send only when `conversations.closed_at` is set (`chat-service/services/message-service/internal/service/message.go:1116-1128`). Only the dating consumer sets it, on `match.closed`, `match.expired` and `user.blocked` (`internal/events/dating_consumer.go:110-140`). The `/dating-match/state` check that graph-service uses for calls reads the same flag.
  - Admin suspend (`service/admin.go:183-192`), automatic risk escalation to `chat_hold`/`suspend` (`service/risk.go:236`, sweeper `:495`), self-delete (`service/profile.go:509-519`) and the platform DPDP deletion consumer (`events/consumer.go:134-149`) change the profile status or the risk row only. None of them closes the open matches or publishes anything chat-service acts on. `chat_hold` is enforced only on new sparks (`service/spark.go:164-180`). Matches close for a deleted user only at the grace purge (`service/dataexport.go:440-458`).
  - Block (`service/safety.go:484-524`) and unmatch (`service/match.go:445-463`) commit the closure in Postgres, then publish `user.blocked` and `match.closed` directly with kafka-go on the request context (`events/producer.go:39-46`, no outbox). A failed publish is logged and the request returns 200. If the client drops the connection after the commit, the context is cancelled and the publish fails. kafka-go's synchronous writer waits for its default 1 s batch timeout per message, so a block that closes one match spends about 3 s in this window.
- **Scenario:** (a) Moderators suspend a romance scammer from a "scam" report. Their chats with ten other matches stay open in message-service, so the scammer keeps messaging those people. The M17 scam alert, where it is enabled, warns the victims while the scammer is still able to reach them. (b) A user blocks a harasser from the chat screen and the app closes the screen at once. The request context is cancelled during the Kafka write, the conversation never gets `closed_at`, and the harasser can still message the user who blocked them, until someone notices.
- **Fix:** Write `match.closed` and `user.blocked` to an outbox table in the same transaction as `BlockUserAndSever` and `CloseMatchWithReason`, using the shared outbox (already fixed on this branch), and relay them from there. On suspend, `chat_hold`, self-delete and DPDP deletion, close the user's open matches in the same transaction and emit `match.closed` for each, as the purge already does. As a backstop, have message-service's dating send gate call dating's internal match-state check when `closed_at` is null, with a short cache.

### H3. The legacy `/v1/dating/admin/*` path admits any consumer session with a ladder role and ignores per-route permissions, including panic GPS reveal and bans
- **Files:**
  - `http/handler.go:283` mounts the admin console under `/v1/dating/admin` with `requireAdmin`. With no service token, `requireAdmin` (`http/auth.go:125-163`) admits any request whose gateway-set `X-Scopes` holds `admin`, `moderator` or `superadmin`, and **never looks at `perms`**. Per-route permissions are enforced only on the token path (`admin_token.go`). The routes include `GET /safety/panic/:id` (`handler.go:321`, `dating:panic.reveal`, exact GPS), `POST /reports/:id/action` (`:316`, suspend and reinstate), `POST /verification/selfie/:userId/review` (`:334`) and `GET /audit`.
  - The gateway treats only `/v1/admin/...` as an admin path (`api-gateway/pkg/adminsession/adminsession.go:52-58`), so `/v1/dating/admin` takes a consumer session, and the gateway stamps that session's scopes (`api-gateway/cmd/server/main.go:1063-1066`). identity keeps the ladder scopes on a consumer token whenever the admin has 2FA and signed in with OTP (`identity-platform/services/auth-service/internal/service/admin_session.go:150-153`, `:175`).
- **Scenario:** A social-side moderator (ladder role `moderator`, with no dating permission in admin-service) signs in to the consumer app with OTP. From that session they call `GET /v1/dating/admin/safety/panic` and `/safety/panic/<id>`, and read the exact coordinates of users who pressed the panic button. They can also suspend or reinstate dating users and pass selfie reviews. admin-service's role model and step-up are bypassed. Today only pilot users reach `/v1/dating`, and the path opens to everyone with `DATING_PUBLIC_ENABLED`.
- **Fix:** Retire the legacy branch: make `/v1/dating/admin` token-only (`requireAdminToken`), as `InternalAdminPrefix` already is. If it must stay for a release, at minimum refuse `PermPanicReveal`, `PermUsersBan` and `PermSelfieReview` on the legacy branch, and add a test showing that a consumer-session `moderator` scope gets 403 on `/safety/panic/:id`.

## MEDIUM

### M1. Verification badges are not bound to the person on the profile
- **Files:** A selfie compares the blink video with the approved primary photo at that moment (`service/verification.go:429`). After a pass, `trust_tier` can only step up (`store/verifications.go:10-11,127-155`). New or replaced photos (`service/photos.go:99`) never reset the tier or ask for a recheck. Aadhaar (`service/verification.go:126-176`) stores an opaque `digilocker_ref` per user (`store/verifications.go:104-112`), with no uniqueness across users and no name, DOB or face binding. One person's DigiLocker sign-in can mark any number of accounts `aadhaar`, the top tier and the one the verified-only filter admits (`store/pulse.go:291-298`).
- **Scenario:** A catfish passes the selfie check with their own face, then swaps every photo for a model's pictures. The deck still shows "selfie verified", and users who filter to verified-only see them. When DigiLocker is turned on, one scammer's Aadhaar can badge a whole farm of accounts.
- **Fix:** When the primary photo changes after a pass, drop the tier to `phone` (or keep it only if a media-service face compare against the stored verification video passes). Store a keyed hash of a stable DigiLocker subject identifier with a unique index, and refuse a second account. Prod has `DIGILOCKER_MODE: disabled`, so the Aadhaar half is latent until then.

### M2. A location share sent to a match survives the unmatch
- **Files:** `service/safety.go:338-388` lets a user share an exact point with a match (`ShareRecipientMatch`) for up to 120 minutes (`safety_config.go:45-46`). `GetLocationShareForRecipient` (`store/location_shares.go:134-147`) checks only the recipient, expiry and blocks. Neither `CloseMatchWithReason` nor the unmatch path stops or clears the share. The only cleanup is a block or the purge (`store/profiles.go:695`).
- **Scenario:** Before a first date, a user shares her live location with the match. The date goes badly and she unmatches him (but does not block him, because blocking feels escalatory). For up to two hours he can still open `GET /safety/shared-locations/:id` and see her exact position.
- **Fix:** For `recipient_kind = 'match'`, add `AND EXISTS (open match for the pair)` to the read, and stop the pair's match shares in the same transaction as the unmatch.

### M3. `GET /vouches/for/:userId` answers for any user id, so it works as an oracle for who has a dating profile and who vouched for them
- **Files:** `http/handler_vouches.go:124-144`, `store/vouches.go:197-225`. Accepted vouches return `voucher_id`, `relationship`, `community_id` and the free-text `note` for any vouchee. The query checks the voucher's visibility and blocks only. It does not check whether the vouchee is visible to the caller, or whether the vouchee is paused, hidden, restricted or under 18.
- **Scenario:** Someone takes a colleague's user id from the social app and calls `/vouches/for/<id>`. A non-empty answer confirms a dating profile, even a paused or hidden one, and names the friends who vouched, their relationship ("college friend", "sister") and the vouch text.
- **Fix:** Serve other people's vouches only where `canViewPerson(viewer, vouchee)` holds, and otherwise return 404. Return the same empty answer for "no profile" and "not visible".

### M4. Every boot re-adds CHECK constraints and rescans `dating_profiles` in one implicit transaction, with no lock_timeout and no cross-replica lock
- **Files:** `database/embed.go:22-31` sends all of `setup.sql` as one `Exec`. Every boot runs `ALTER TABLE dating_profiles DROP/ADD CONSTRAINT` four times (`setup.sql:525-543,558-574`). Each takes an ACCESS EXCLUSIVE lock and the ADD validates with a full scan. The script also runs the backfill `UPDATE`s at `:618-660`, whose `WHERE` evaluates `EXISTS` subqueries per active or paused row on every boot. All of these locks are held until the whole script commits. Unlike food, there is no advisory lock and `lock_timeout` is never set.
- **Scenario:** On a rolling deploy, the new pod boots while the old pod is serving decks (`FetchCandidates` with `ORDER BY random()` over the city). The new pod's `ALTER TABLE` queues behind those reads, and every profile read and write (decks, sparks, person cards, location updates) queues behind the ALTER until the script finishes. A worker or north-star binary that boots at the same time (`cmd/north-star/main.go:50`) runs the same script concurrently.
- **Fix:** Guard each constraint with `IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = ...)`, add it `NOT VALID` and validate it once. Put the one-off backfills behind an existence check. Start the script with `SET lock_timeout = '5s'`, and take a `pg_advisory_xact_lock` as food does.

## LOW

### L1. The cached deck outlives risk escalation and platform deletion
With `DATING_DECK_REFILL_ENABLED` off (the prod default), `/pulse/today` serves the Redis deck for 24 h without re-filtering it (`service/pulse.go:154-163`). Block, pause, delete, photo and admin actions invalidate it. Risk recompute (`service/risk.go:236`) and the DPDP deletion consumer (`events/consumer.go:144`, which holds only the store) do not. A user the sweeper moves to `hide_from_discovery` or `suspend` stays in others' decks for up to a day, and `PhotoAudience` (`store/photo_safety.go:279-284`) does not read risk, so their photos still load. **Fix:** call `InvalidateDecksForCandidate` when the risk level crosses into a hiding level, and give the platform consumer the service (or a Redis handle) so it can do the same.

### L2. A mutual spark whose match formation fails is lost
`createSpark` logs `form match after mutual spark failed` and returns success (`service/spark.go:271-293`). If the failure happens before `CreateOrGetOpenMatch` inserts a row (for example a transient error in `requireInteractiveProfile`), the saga reconciler has nothing to retry, and the pair never matches. **Fix:** when the reverse spark exists, return the error so the client retries, or insert a pending-match row first so the reconciler finishes the match.

### L3. Discovery and Nebula cost
- The deck query sorts the whole filtered set with `ORDER BY random()` (`store/pulse.go:410-416`). In a metro the 9-cell, precision-4 prefilter covers about 120 km × 120 km. With travel on, the prefilter becomes `COALESCE((correlated subquery), p.location_geohash) LIKE ...` (`store/travel.go:39-44`, `store/pulse.go:392`). That expression is not sargable, so `idx_dating_profiles_geohash_prefix` is skipped and every active profile is scanned.
- Nebula runs one `GetCandidateForViewer` per pass, up to 100 sequential queries per call (`service/pulse.go:636-643`).
- **Fix:** sample with `TABLESAMPLE` or a random key range before sorting. Filter travelling and home locations as two indexed branches. Batch Nebula into one `user_id = ANY($ids)` query.

### L4. Minor
- `PhotoImageURL` (`service/photos.go:315-331`) serves an approved `public` photo to anyone who holds its id while the owner is paused or has `visible_to_public=false`. `OwnerVisible` checks only deleted, suspended, blocks and incognito. Photo ids are random UUIDs, so this reaches only people who already saw a card.
- Kind-check note filtering sets `note_hidden` but still sends the note text (`service/kind_check.go:210-233`, `store/sparks.go:23,33`), so the filter exists only in the client.
- The age gate prefers identity's birth date but accepts a client-supplied one when identity has none (`service/profile.go:288-303`). Once identity reports an under-18 date, the profile is restricted, but H1 still shows restricted profiles.

## Checked and sound
- **Location:** stored points are snapped to a 0.01° grid (about 1.1 km) in Go and in SQL, and the geohash is derived from the snapped point (`store/geo.go:204-219`). Clients never send a geohash. Every response carries a distance bucket (`<5`, `5-10`, `10-25`, `25+` km), never a number, and ranking uses the bucket's representative value. The deck radius rounds up to steps (`EffectiveDiscoveryRadiusKm`). Location changes are limited to one per 15 min and 10 a day (`store/location.go:43-45`). Travel uses a fixed city list. `store.Profile` latitude and longitude go only to the owner (`GET /profile`) and the owner's export. Exact points (panic, location shares) are sealed with the PII keys, and admin GPS sits behind `dating:panic.reveal` with audit on the token path (H3 aside).
- **Photos:** media-service re-encodes the original with EXIF, GPS, XMP and IPTC removed before the first delivery (`media-service/internal/processing/dating_photo.go:17-20`). Cards carry only `/v1/dating/photos/:id/{full|blurred}`, which decides access on every fetch and redirects to a 30-300 s signed URL. Blurred and full variants follow `PhotoVariantFor` (match, sparked-only, blur-until-match). Liked-you photos are always the blurred variant.
- **Blocks:** one transaction writes the block, closes the open match, and deletes sparks and stashes both ways (`BlockUserAndSever`). Both decks are invalidated. The deck, person card, incoming sparks, vouches, match view, location shares and match formation (`CreateOrGetOpenMatch` refuses a blocked pair inside the insert) all filter blocks in both directions. The chat closure is the gap described in H2.
- **Person card:** `canViewPerson` requires an open match, an unlocked incoming spark, a recent pick, or presence in the current deck, plus no block either way. The caller must be an adult.
- **Liked-you:** when the gate is on, a caller without the pass gets spark ids, timestamps and a blurred photo only. Accept refuses without the entitlement, the `spark.created` event reveals the sender only to entitled recipients, and a failed premium lookup locks the gate.
- **Sparks and matches:** the spark quota sits in a never-deleted ledger under a per-user advisory lock (50 per rolling 24 h). Super Sparks are charged in the same transaction. Notes with phone numbers, emails or links are refused. A candidate must be active, 18+ and unblocked, and the decline cooldown is honoured. Concurrent mutual sparks converge on one row through `uq_dating_matches_open_pair` (`store/matches.go:123-165`). Boot refuses to start with duplicate open matches unless the dedupe flag is set. Only the creating call runs the chat saga, and the reconciler finishes stuck sagas. Match reads and actions check participants.
- **Premium:** the client never sends an amount. The payment-event inbox and the effect share one transaction, with the purchase row `FOR UPDATE`. `CheckCapture` uses `RequireStated` (amount, currency, payer, intent). `moneyTaken` blocks a double grant. Refunds are capped at what remains, and pass time is clawed back pro rata. Unused boost and Super Spark units are taken back, and spent ones are recorded. Entitlement checks read `expires_at > now()`, computed in the database.
- **Data export and deletion:** downloads are scoped to the owner (`OpenExportPayloadForOwner`, `no-store`). Reports against the user are exported without the reporter, details or exact time. The grace purge deletes the user's rows, including location shares (`store/profiles.go:695`), releases media claims, and closes matches with `match.closed`.
- **Service edge:** `/v1/dating/*` requires the internal key, and the `/internal/` routes require a service token or the legacy key and refuse any request that carries a user identity. message-service's dating-match create, opening-answer and read-receipt routes are internal-key only and refuse user identity. The gateway strips client identity headers, including `X-Admin-Id` and `X-Internal-Key` (`main.go:845-866`).
- **Rate limits:** sparks 50 a day, Super Sparks 1 (free) or 5 (pass), reports 10 a day, panic 5 a day, location 10 a day, selfie attempts capped with a 5-attempt default, deck size capped when refill is on, and message sends limited in message-service.
- **Workers:** prod runs one replica. The match dedupe takes an advisory lock, and the selfie, panic and premium-reminder claims use row claims.
